# Восстановление общей службы Continuator

Один процесс на пользователя Windows управляется **одной задачей Windows Task
Scheduler**, а не моделью и не цепочкой наблюдателей. Задача запускается при входе
пользователя и имеет повтор каждую минуту, чтобы восстановить даже пропавший или
неожиданно успешно завершившийся процесс. RestartOnFailure дополнительно повторяет
ошибочный запуск через минуту. IgnoreNew и освобождаемый ОС межпроцессный lock
исключают параллельные Continuator. Батарея и таймаут выполнения не выключают задачу.
Пароль не хранится; используется InteractiveToken текущего пользователя с обычными
правами. Выйдя из Windows, пользователь завершает эту сессию; при новом входе
служба запускается снова. Планировщик должен быть включён, задача не отключена.

## Установка

`install_continuator_task.ps1 -HomeDirectory <service-home> -PythonExecutable <python.exe>`
регистрирует одну задачу CD5 Continuator, сохраняет прежнее определение, запускает
её и удаляет только относящийся к ней прежний HKCU Run с резервной копией.
Установка явно авторизуется пользователем. `setup_shared_continuator --install-logon`
использует этот установщик. Обновление навыка само по себе не включает controls.
Не применять PreserveRunEntry вне ограниченного технического испытания миграции.

Перед заменой действующего процесса убедиться, что он относится к точному home и
скрипту, и не оставить параллельную прежнюю службу. Другие задачи Windows и чужие
проекты не трогать. Текущие владельцы HQ берутся из CHECKPOINT при каждом проходе.
Состояния continue_HQ/suspend_HQ установка и восстановление не меняют.

## Диагностика

- SERVICE.log — ограниченный по размеру журнал запуска, изменений состояния,
  ошибок, восстановления записи и штатного/аварийного выхода; 1МБ и три архива.
  Одинаковые ошибки ограничиваются одной записью в минуту. Если основной каталог
  недоступен при запуске, журнал пробуется в LOCALAPPDATA/CD5.
- PROCESS.json и HEARTBEAT.json — PID, уникальный экземпляр, время создания процесса
  Windows и свежесть heartbeat. STATUS.json с прежним connected сам по себе
  не доказывает живую службу. `shared_continuator.py --home <home> --health`
  проверяет живой процесс, его время создания и heartbeat не старше90 секунд.
  Для внешнего процесса нужны права чтения; недоступная проверка не является
  доказательством смерти или здоровья. Healthy означает живой отзывчивый процесс,
  отдельно показываются connected/waiting_for_desktop и успешность записи STATUS.
  Повторный триггер IgnoreNew может записать отказ нового запуска, пока прежний
  экземпляр работает. Один LastTaskResult без проверки PID/heartbeat не доказывает падение.
- EXIT.json — наблюдение штатного выхода или перехваченной ошибки; при внешнем
  принудительном завершении процесс не может записать собственный EXIT. Новый
  запуск виден в SERVICE.log и PROCESS.json; результат ОС-задачи проверяется отдельно.

Временный отказ записи PROCESS/HEARTBEAT/STATUS не выбрасывается наружу из цикла:
он журналируется, следующая итерация повторяет запись. Состояние отправки каждого
HQ остаётся строгим: неизвестный результат не повторяется вслепую. Ошибка одного
HQ не останавливает проверки другого. При пропаже настоящего соединения Codex
клиент закрывается и переподключается с задержкой2–30 секунд без модели. Pipe и
учётные данные не придумываются, независимый app-server не создаётся.

## Проверка и пределы

На явно разрешённом техническом стенде подтвердить цепочку: задача работает →
завершить только проверенный PID → без ручного запуска ОС создаёт новый PID →
heartbeat свежий → настоящее соединение восстановилось → один экземпляр и controls
не менялись. Отдельно проверить временную недоступность копии descriptor и отказ
записи тестового состояния. Не выключать пользовательский Codex/Windows и не
запускать исследование ради испытания службы.

Это восстановление пропавшего/аварийного процесса в работающей пользовательской
сессии и при работающем Планировщике, не обещание абсолютной доступности Windows.
Отключённая ОС-задача, неисправность самого Планировщика, отсутствие места/прав,
выход из учётной записи и глобальное зависание ОС требуют отдельной диагностики.
Не выдавать kill/restart за фактически проверенный reboot или вход Windows.
